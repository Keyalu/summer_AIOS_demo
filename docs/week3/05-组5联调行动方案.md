# 组 5 联调行动方案 —— 分组四 Tools 层 × 组 5 Coordinator / Security / RAG

> 配套材料：《02-组间集成指南.md》（接口契约）、`tests/test_integration_group5.py`（6 个审计接入测试）
>
> 一句话：**组 5 不调用我们的工具，组 5 消费我们调用的"痕迹"。联调内容 = 让组 5 的 check_json 能解析、能审计、能存档我们的三种输出。**

## 一、组 5 在流水线里吃我们什么

按《01-MCP协议调研报告》五组数据流：

```
组1 HostAgent → 组2 TaskPlanner → 组3 AppAgent → ★组4 Tools → 组5 Coordinator: 审计并存储
```

组 5 的三个角色，对应我们三种输出：

| 组 5 角色 | 吃我们的什么 | 我们的产出物（已存在，零开发） |
|-----------|-------------|------------------------------|
| **Coordinator（审计存储）** | 每次调用的明细记录 | `BufferedToolStats` 落盘的 `stats.json`（time/tool/params/success/duration_ms/error） |
| **Security（安全）** | 失败事件（参数错误/执行异常，带分类前缀） | 统计里的 fail 记录。**注意**：权限拦截发生在统计之前（调度层拒绝不产生调用记录，这是与组3定死的契约），权限事件不进审计日志——Security 如需，走"推模式 callback"（见第三节问题 1） |
| **RAG（知识）** | 工具能力描述 | `list_tools()` → `ToolSchema.to_dict()` = MCP 风格 inputSchema |

**关键优势：三种输出全是纯 JSON，组 5 不需要 import 我们的代码就能消费——他们的联调可以完全独立进行。**

## 三、联调前要和组 5 对齐的 4 个问题

1. **审计是"拉"还是"推"？**
   - 拉模式（推荐先做）：组 5 定时读我们的 `stats.json`（BufferedToolStats 每 5 秒或每 200 条原子落盘一次）。
   - 推模式（如需再加）：我们加一个 audit callback 钩子，每次调用后推送 JSON——半天工作量，联调时确认了再做。

2. **caller_level（调用者身份）由谁定？**
   - 现状：组 3 调用时自报 USER/ADMIN，Registry 强制校验工具要求的级别，拦截事件进审计日志。
   - 要确认的：组 5 的 Security 是否要**下发**权限策略（如黑名单工具、临时降级）。我们的权限模型支持，但需要组 5 给出策略格式。
   - **契约提醒**：当前权限拦截不产生调用记录（调度层拒绝、与组3契约一致）。Security 若要求"每次拦截都留痕"，属于新需求——我们加安全事件 callback，不改现有统计口径。

3. **check_json 校验的是什么？**
   - 建议：用我们的 `inputSchema` 校验组 3 发来的调用参数（可参考 `test_integration_group5.py` 里用 inputSchema 验参数的写法），用 `{success, result/error}` 结构校验我们的返回。

4. **审计日志的保留与脱敏？**
   - stats.json 里 params 含文件路径。若组 5 的 Security 要求脱敏（如抹掉用户名），约定脱敏规则——建议在组 5 侧做，保持我们输出"如实记录"。

## 四、联调当天：三阶段递进（每阶段有通过标准）

### 阶段 1：契约自查（15 分钟）—— 组 5 独立可做

组 5 拿到 zip 后，不用我们的代码，只跑一个"消费模拟"：

```bash
cd linux-agentic-os-group4
python -m pytest tests/test_integration_group5.py -v   # 6 个测试应全绿
```

**通过标准**：全绿。这 6 个测试 = SimulatedCoordinator 用纯 JSON 方式消费我们的输出，等价于组 5 的 check_json 接入的最小验证。

### 阶段 2：审计接入（30 分钟）—— 核心一步

组 5 在自己的 Coordinator 里实现"读取并存储"：

1. 我们这边跑几轮演示（`python demo_io.py` 或组 3 的流程），产生 `stats.json`；
2. 组 5 解析该文件：`records`（明细时间线）+ `counters`（聚合报表）+ `updated`（更新时间）；
3. 组 5 验证：能数出 fail 事件、能按 tool 分组、能按 time 排序。

**通过标准**：组 5 的审计存储不接触我们任何 Python 对象，只吃 JSON——如果他们想 import 我们的类，说明集成方式偏了（不禁止，但纯 JSON 是解耦底线）。

### 阶段 3：五组全链路演练（60 分钟）—— 课程的高潮部分

端到端剧本（每组的接口各出场一次）：

| # | 步骤 | 数据 | 演示看点 |
|---|------|------|---------|
| 1 | 组 1 解析"整理下载文件夹" | intent_json | 自然语言 → 结构化意图 |
| 2 | 组 2 规划步骤 | plan_json | 意图 → use_skill 步骤 |
| 3 | 组 3 执行并调我们 | 调用参数 | Agent 决策 |
| 4 | **组 4 执行** | tool_result_json | 三道闸门 + 统一返回（本演示） |
| 5 | **组 5 审计** | stats.json | 调用记录落盘 → 组 5 存档 → 向用户出示"本次任务审计报告" |

**通过标准**：组 5 出示的审计报告数字（调用次数/成功数/失败数）与我们的 `stats.report()` 完全一致。
