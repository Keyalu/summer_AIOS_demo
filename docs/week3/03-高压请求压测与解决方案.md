## 三、关键发现：瓶颈不在架构，在 IO 层

压测最重要的结论是一条**分界线**：

```
纯内存路径（Registry 核心）          磁盘 IO 路径（文件/统计）
─────────────────────────          ─────────────────────────
注册 1 万工具:   268k ops/s   ✅    扫 1 万文件:      92 ops/s    🔴
查询:           0.13 µs      ✅    搬 3 千文件:      69 ops/s    🔴
并发 8 千调用:   87k ops/s    ✅    并发+落盘:        17 ops/s    🔴
MCP 5 千调用:    90k ops/s    ✅    落盘 1 千条:      53 s        🔴
```

**Registry 调度层（权限检查、字典查找、JSON-RPC 协议转换）全是 O(1) 且线程安全**（S5 的 8,000 次并发零丢失）。拖垮系统的全部是**磁盘 IO 的用法不当**。这意味着：不需要重构架构，只需要**预设正确的 IO 策略**。

### 根因逐个拆解

**根因 1：`list_directory` 的 stat 放大（S2: 108 秒）**

`default_tools.py` 中对每个文件做了 **2 次 stat**（`p.is_file()` 一次 + `p.stat()` 一次），而 `pathlib.Path` 每次属性访问都是独立的系统调用：

```python
for p in sorted(base.iterdir()):          # 1 万次迭代
    "type": "dir" if p.is_dir() else "file",        # stat 第 1 次
    "size": p.stat().st_size if p.is_file() else None,  # stat 第 2、3 次
```
1 万文件 × 3 次 stat ≈ 3 万次系统调用 + Windows Defender 逐文件扫描 → 108 秒。且结果**只取前 100 条**，99% 的 stat 是白做的。

**根因 2：统计模块每次 record 全量重写 JSON（S6: O(n²)）**

`stats.py` 的 `record()` 每记录一条就调用 `_save()`，而 `_save()` 把**所有历史记录**重新序列化写盘：

```python
def record(self, record):
    self._records.append(entry)
    ...
    if self._log_path:
        self._save()      # ← 每条都全量重写！第 n 条时写 n 条数据
```
总写入量 = 1+2+3+...+n = **n²/2 条记录**。1000 条调用实际写了 50 万条的数据量（53 秒）。

**根因 3：并发场景下根因 2 被线程竞争放大（S5b: 17 ops/s）**

16 个线程同时调用 `call()` → 同时触发 `_save()` → 锁竞争 + 磁盘排队。纯内存时 87,000 ops/s，一加磁盘落盘掉到 **17 ops/s**（差 5,000 倍）。

**根因 4：统计明细列表无上限（S8: 150.9 MB）**

`_records` 只进不出，20 万次调用吃掉 150.9 MB；按此速率，一天 50 万次调用会让长驻进程内存膨胀到 400 MB+。

## 四、解决方案：三层"预设方案"

### 方案 1【已实现 ✅】缓冲批量统计 —— `src/stats_buffered.py`

新增 `BufferedToolStats`，与 `ToolStats` **接口完全一致、可一行替换**：

```python
# 旧：stats = ToolStats(log_path="stats.json")
# 新：
stats = BufferedToolStats(log_path="stats.json")   # 无缝替换
reg = ToolRegistry(stats=stats)
```

三个预设策略：
1. **批量落盘**：攒满 200 条、或每 5 秒，才写一次磁盘（A2 实测 **177.7×** 提升）
2. **环形缓冲**：内存只保留最近 5,000 条明细，计数器不受影响（解决 S8 内存膨胀）
3. **线程安全**：`threading.Lock` 保护计数与落盘（解决 S5b 竞态）

**代价**：崩溃时最多丢最近 5 秒的明细（计数器仍在）。对监控系统是可接受的 trade-off。

### 方案 2【已实现 ✅】`os.scandir` 替代 `Path.iterdir` —— 实测 2146×

`list_directory` 已重写为 scandir 版本，并叠加分页（见方案 3）。实测 **10000 文件从 108.55s → 0.05s，提升 2146 倍**：

- scandir 在 Windows 上随目录项免费返回文件类型/大小，免去每文件 2~3 次 stat 系统调用
- 页外条目只计数、不做 stat——系统调用总量从 O(全目录×3) 降为 O(页大小)
- `count` 语义与旧版完全一致（返回目录总条目数），调用方无感升级

### 方案 3【已实现 ✅】分页与游标——不让单次调用吞下 1 万结果

`list_directory` 已支持可选参数 `offset` / `limit`（默认行为与旧版一致）：

```python
r = reg.call("list_directory", {"path": d, "offset": 100, "limit": 100})
# → {"count": 10000, "returned": 100, "entries": [...],
#     "has_more": True, "next_offset": 200}
```

翻页由 `has_more` / `next_offset` 驱动，直到 `has_more=False`。单页上限 1000，
防止一次调用吞下万级结果。实测第二页耗时仅 **47.8ms**。

### 方案 4【已实现 ✅】Worker Pool + 有界队列 + 背压 —— `src/batch_executor.py`

已实装 `BatchExecutor`，把"一次处理 1 万个文件"变成"8 个工人从传送带上取活"：

```python
with BatchExecutor(registry, workers=8, max_queue=2000) as ex:
    for task in tasks:
        ex.submit(task["tool"], task.get("params", {}))  # 队列满→阻塞(背压)→超时拒绝
    results = ex.drain()      # 阻塞收割全部结果
print(ex.stats())             # submitted/completed/succeeded/failed/rejected
```

三个"预设"全部落地：
- **并发度预设**：workers=8（磁盘 IO 密集，约等于 CPU 核数即可）
- **队列容量预设**：max_queue=2000，满了让提交方等——**背压**保护系统不被压垮；等待超过 block_timeout 则拒绝（返回 False），调用方可降级
- **健壮性**：worker 线程吃掉一切工具异常（工具崩溃不杀死工人），已由 `test_worker_survives_tool_crash` 验证

### 方案 5【已实现 ✅】查重两级过滤 —— 实测 13.8×

`find_duplicate_files` 已重写为两级过滤，实测混合数据（2000 文件、1900 唯一 + 50 对重复）：
**全量哈希 7.34s → 预分组 0.53s，提升 13.8×**（只对 100/2000 个嫌疑文件算哈希）：

- 第一级：按文件 size 分组（纯 stat，不读内容）→ size 互不相同的文件不可能重复
- 第二级：只对 size 撞车的"嫌疑组"算分块 MD5
- 返回体新增 `scanned`（扫描总数）与 `hashed`（实际哈希数），可直观看到过滤效果
- 全部唯一时 `hashed=0`——哈希量直接降为零（已由测试验证）

### 方案 6【已实现 ✅】限流与熔断——`RateLimiter` + `CircuitBreaker`

已在 `src/batch_executor.py` 中实现两个防御组件，可独立使用也可挂进 BatchExecutor：

**RateLimiter（令牌桶限速器）**——预设每秒最多执行 N 个任务，worker 拿不到令牌就睡眠等待：

```python
limiter = RateLimiter(rate_per_sec=500)          # 预设速率上限
with BatchExecutor(reg, workers=8, rate_limiter=limiter) as ex:
    ...                                          # 执行速率被钉死在 500/s
```

**CircuitBreaker（失败率熔断器）**——累计 min_samples 个结果后评估，
失败率超阈值即熔断：后续任务**不再真正执行**，直接返回
`ToolResult.fail("熔断: 失败率超阈值，任务被中止")`，冷却 cooldown 秒后自动半开：

```python
cb = CircuitBreaker(failure_threshold=0.5, min_samples=20, cooldown=30)
with BatchExecutor(reg, workers=8, circuit_breaker=cb) as ex:
    ...                    # 系统性故障时 50 个任务只真正执行约 20 个，其余快速失败
```

**三档预设一键启用**（`BatchExecutor.preset(registry, 档位)`）：

| 档位 | workers | max_queue | rate_per_sec | 适用场景 |
|------|---------|-----------|--------------|---------|
| light | 2 | 200 | 50 | 个人桌面、轻量任务 |
| medium | 8 | 2,000 | 500 | 日常自动化 |
| high | 16 | 10,000 | 不限速 | 万级文件批量 |

### 方案 7【已实现 ✅】技能并行化——`organize_downloads(workers=N)`

整理技能新增 `workers` 参数（默认 1，行为与旧版完全一致）：

- **规划阶段单线程**：分类 + 重名消解（`_dup1/_dup2` + `reserved` 集合防并行撞名），产出 `(源, 目标)` 清单——目标路径在规划期就保证唯一
- **执行阶段线程池**：`ThreadPoolExecutor` 并行 `shutil.move`

**双平台实测（2000 个小文件）**：

| 平台 | workers=1 | workers=4 | workers=8 | 结论 |
|------|-----------|-----------|-----------|------|
| Windows | 5.63s (355 f/s) | **3.17s (630 f/s, 1.8×)** | 5.25s | 4 线程最优；8 线程磁盘竞争反而变慢 |
| WSL Linux | **0.22s (9277 f/s)** | 0.83s | 0.84s | 同盘 move=rename（纯元数据），串行已极快，并行是负优化 |

> 工程结论（汇报时的诚实口径）：并行化收益取决于瓶颈在哪里。
> Windows 上每个文件操作有安全软件扫描等固定开销，4 线程可摊薄 → 1.8×；
> Linux 上同盘 rename 只是改目录项，串行已近万文件/秒，无需并行。
> **所以 workers 做成预设参数而不是写死**——这正是"预设方案"的意义。

## 七、对组间契约的影响：零破坏

所有方案的共同原则：**接口不动，只升级实现**。

- `BufferedToolStats` 与 `ToolStats` 实现同一个 `IToolStats`，组 3 的代码一行不改即可受益；
- 分页参数是可选参数（`offset=None` 时行为与旧版完全一致）；
- Worker Pool 是 Registry 之上的**可选编排层**，不改变 `IToolRegistry.call()` 的同步语义；
- 这正是第 1 周定义抽象接口的价值：**Mock 和真实实现可替换，慢实现和快实现同样可替换**。
