# 分组四进度检查讲解指南

> **适用场景：** 明天下午的进度检查汇报
> **核心原则：** 先讲"我们是谁"，再讲"做了什么"，最后讲"做到什么程度了"
> **讲解时长建议：** 5-8 分钟

---

## 一、开场白（30 秒）

**话术模板：**

> "老师好，我们是**分组四，负责 Tools + OS Skills 模块**。
> 简单来说，整个系统有 5 个组，我们组的位置是——**夹在组 3（AppAgent）和 Linux 操作系统之间**，相当于给 AI Agent 装了一双手，让它能操作文件系统、执行命令。"

**配合动作：** 可以画一个简单的流水线图（下文有）。

## 二、我们负责什么（1 分钟）— 用比喻讲清楚

### 不要这样说：
> "我们实现了 ToolRegistry 和 SkillLibrary，支持 register、call、unregister 方法..."

### 要这样说：

> "想象一下，AI Agent 就像一个**只会说话的客服**——它能听懂用户要干什么，但手伸不出去操作电脑。
>
> 我们做的东西就是给这个 Agent **装一双手**：
>
> - **ToolRegistry（工具箱）** — 相当于一把瑞士军刀，里面有复制文件、移动文件、执行命令等 8 个基本工具
> - **SkillLibrary（技能库）** — 相当于**一键宏命令**，比如'帮我整理下载文件夹'这一个技能，内部自动完成：扫描 → 分类 → 创建文件夹 → 搬迁
> - **MCP 连接器** — 相当于一个**USB 接口**，未来可以插外部工具进来（搜索、翻译、天气查询等）
>
> 组 3 的 AppAgent 需要做文件操作时，就调我们的接口；我们做完后把结果返回给它。就这么简单。"

## 三、两周一共做了什么（2 分钟）— 分阶段讲

### 第 1 周：打地基（调研 + 定规矩 + 做样品）

## 六、可能被问到的问题及回答（提前准备）

### Q1："你们的权限控制是怎么做的？"

> "我们设计了三级权限模型——public、user、admin。
>
> - **public**：只读操作，谁都能调用（比如查看目录内容）
> - **user**：普通文件操作（复制、移动、删除）
> - **admin**：危险操作（执行 shell 命令），需要显式传 admin 权限才能调用
>
> 另外，我们还做了两层安全过滤：**危险命令黑名单**（比如 `rm -rf /` 直接拦截）和**受保护路径检查**（不能删 `/etc`、`/usr` 这种系统目录）。"

### Q2："Mock 是干嘛的？为什么一定要做？"

> "Mock 解决的是**并行开发依赖问题**。5 个组同时开工，如果组 3 必须等我们写完才能开始，那就串行了。
>
> 我们提供 Mock 版本后，组 3 第一周就可以 import 我们的 Mock 来写自己的代码，完全不需要等我们。Mock 和真实实现共享同一套接口定义，切换时只需改一行 import。"
>
> （类比：就像建筑队先搭个脚手架，装修队可以先上去干活，不用等楼盖完。）

### Q3："MCP 协议这部分做到了什么程度？"

> "目前是 **Mock 实现**——我们模拟了 MCP Server 的连接管理和 JSON-RPC 2.0 通信格式。
>
> 具体来说，我们实现了三个 Mock 外部工具（搜索、天气、翻译），它们的返回值严格遵守 MCP 的 `tools/call` 格式。这为后续接入真实的 MCP Server 打好了基础——接口已经定型了，将来只需要替换底层实现就行。"
>
> （任务书也明确写了 MCP 可以用 Mock 实现，占 5 分）

### Q4："你们三个人是怎么分工的？"

> （根据实际情况调整）
> "我们三个人的工作最终合并成了一个版本——
> - 同学 A 的贡献：模块化架构设计、接口抽象层、Mock 双模式实现、调用统计模块
> - 同学 B 的贡献：三级权限体系、备份/查重技能、JSON-RPC 2.0 Mock 格式、正式设计报告
> - 我的贡献：项目骨架搭建、8 个默认工具、MCP Server 管理、完整测试套件（125 个）、文档整合
>
> 最终合并版吸收了每个人的优点，形成了现在这个 10 模块 + 125 测试的项目。"
