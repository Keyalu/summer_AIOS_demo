# 02-验证原理详解 — 三种验证方式的工作原理

> **目标**：让你能回答"你们的测试是怎么做的？"这个问题

---

## 核心问题

**"你们怎么证明代码是正确的？"**

我们有**三种验证方式**，从简单到严格，层层递进：

```
main.py（演示）  ←  quick_check.py（半自动）  ←  pytest（全自动）
   人眼判断            手写assert判断              框架自动判断
```

三者调用的是同一套源码（`src/`目录），区别在于 **"谁来判定PASS/FAIL"**。

---

## 方式1：main.py 自动演示

### 原理：顺序执行 + 打印结果 + 人眼判断

```python
def demo():
    # Step 1: 创建对象
    registry = ToolRegistry()

    # Step 2: 调用方法
    r = registry.call("run_command", {"cmd": "echo hello"}, PermissionLevel.ADMIN)

    # Step 3: 打印结果（让开发者看对不对）
    print(r.to_dict())
    # 输出: {'success': True, 'result': 'hello\n'}
```

### 底层发生了什么？

| 步骤 | 内部机制 | 对应源码位置 |
|------|---------|-------------|
| `ToolRegistry()` | 构造函数 → 注册8个默认工具到 `self._tools` 字典 | `tool_registry.py:27-31` |
| `.call("run_command", ...)` | ①查字典→②检查权限→③执行函数→④包装成 ToolResult | `tool_registry.py:62-125` |
| `.to_dict()` | 返回标准格式 `{"success": bool, "result\|error": ...}` | `interfaces.py` |

### 谁来判断对错？👉 **你的眼睛**

- ✅ 直观：能看到完整的数据流
- ❌ 无法自动化判断
- 🎯 适用场景：演示、调试、向别人展示功能

## 方式2：quick_check.py 快速验证

### 原理：手写 check() 函数做布尔判断

```python
def check(name: str, condition: bool) -> None:
    """自定义的判断函数"""
    status = "PASS" if condition else "FAIL"
    print(f"  [{status}] {name}")        # 打印状态
    if not condition:
        raise AssertionError(name)       # 失败就终止程序

# 使用示例：
reg = ToolRegistry()
result = reg.call("run_command", {"cmd": "echo hello"}, PermissionLevel.ADMIN)
check(
    "admin 可执行命令",                    # 检查名称（给人看的）
    result.success and "hello" in result.result  # 布尔表达式（机器判断）
)
```

### 执行流程图解

```
check("admin 可执行命令", result.success and "hello" in result.result)
│
├── result.success → True (布尔值)
├── "hello" in result.result → True (字符串包含判断)
├── True and True → 最终条件 = True
│
├── 条件为 True → 打印 [PASS] admin 可执行命令 ✓
└── 继续下一个检查...

───────────────────────────────

check("危险命令被拦截", not result.success and "拒绝执行" in result.error)
│
├── not result.success → False 变 True (取反)
├── "拒绝执行" in result.error → True
├── True and True → 最终条件 = True
│
├── 条件为 True → 打印 [PASS] 危险命令被拦截 ✓
└── 继续下一个检查...
```

### 谁来判断对错？👉 **手写的布尔表达式**

- ✅ 半自动化：不需要人眼看每个结果
- ✅ 无需安装pytest
- ❌ 需要自己写check逻辑
- 🎯 适用场景：WSL等未安装pytest的环境快速验证

## 方式3：pytest 完整测试套件

### 原理：专业测试框架驱动

这是最严格的方式。pytest 是业界标准的Python测试框架。

#### (1) 测试发现机制

pytest 如何找到测试文件和测试函数？

```bash
python -m pytest tests/test_all.py -v
```

**内部流程**：

```
① 读取 test_all.py 文件
② 扫描所有以 test_ 开头的函数
③ 发现它们属于哪个类（TestToolRegistry / TestSkillLibrary / ...）
④ 构建测试树：

tests/test_all.py::TestToolRegistry::test_default_tools_registered     [1/31]
tests/test_all.py::TestToolRegistry::test_register_custom_tool         [2/31]
...
tests/test_all.py::TestIntegration::test_full_data_flow               [31/31]
```

**命名约定**：
- 文件名必须包含 `test_` 或以 `_test.py` 结尾
- 函数名必须以 `test_` 开头
- 类名必须以 `Test` 开头
- 这是 pytest 的发现规则

#### (2) 生命周期管理（隔离性保证）

每个测试类都有 `setup_method()` 方法：

```python
class TestToolRegistry:

    def setup_method(self):
        """
        ⚡ 关键：每个测试方法执行前都会先运行这个！
        确保每个测试都在全新的、干净的环境中运行
        """
        self.registry = ToolRegistry()  # 每次都创建新实例

    def test_default_tools_registered(self):
        # 此时 self.registry 已经准备好了
        assert self.registry.has("copy_file")  # 断言1
        assert self.registry.has("move_file")  # 断言2
        ...

    def test_permission_admin_required(self):
        # 又是一个全新的 self.registry！
        # 即使上个测试删了工具也不影响这里
        result = self.registry.call("run_command", ...)
        assert result.success is False  # 断言
```

**为什么重要？**
- 测试A删除了一个工具 → 不影响测试B（因为每次都是全新对象）
- 这叫**测试隔离**

#### (3) 断言机制（智能错误提示）

pytest 重写了Python的assert，提供详细错误信息：

普通Python assert失败时：
```python
assert 1 == 2
# 输出：AssertionError（不知道哪里错了）
```

pytest assert失败时：
```python
assert result.success is False
assert "权限不足" in result.error

# 如果失败，pytest会输出：
# ==================================== FAILURES ====================================
# TestToolRegistry::test_permission_admin_required
#
# def test_permission_admin_required(self):
# >   assert result.success is False
# E   AssertionError: assert True is False
# E    where True = <ToolResult object at 0x...>.success
# E    期望值(期望): False
# E    实际值(得到): True

# >   assert "权限不足" in result.error
# E   AssertionError: assert '拒绝执行' in '未知错误'
# E    其中 '拒绝执行' = <ToolResult object at 0x...>.error
```

**pytest告诉你**：期望什么、实际得到什么、差异在哪里

#### (4) 完整测试用例拆解

以 `test_dangerous_command_blocked` 为例（安全机制测试）：

```python
def test_dangerous_command_blocked(self):
    """
    测试目标：验证危险命令能否被正确拦截
    """
    # 调用工具：尝试执行 "rm -rf /"
    r = self.registry.call(
        "run_command",
        {"cmd": "rm -rf /"},           # 危险命令！
        PermissionLevel.ADMIN,         # 用最高权限
    )

    # 断言1：应该失败（success应该是False）
    assert r.success is False

    # 断言2：错误信息要包含"拒绝执行"这几个字
    assert "拒绝执行" in r.error
```

**底层完整调用链**（一行行追踪）：

```
test_dangerous_command_blocked() 开始执行
│
├── setup_method() 已执行完毕
│   └── self.registry = 全新的 ToolRegistry() 实例
│       └── _register_defaults() 已注册8个工具
│
├── self.registry.call("run_command", {"cmd": "rm -rf /"}, ADMIN)
│   │
│   ├── [tool_registry.py:78] 工具存在性检查
│   │   └── "run_command" in self._tools? ✅ 是
│   │
│   ├── [tool_registry.py:82-87] 权限检查
│   │   ├── schema.permission = ADMIN (run_command需要ADMIN权限)
│   │   ├── user_level = ADMIN (传入的是ADMIN)
│   │   └── ADMIN.rank() >= ADMIN.rank()? ✅ 通过（3 >= 3）
│   │
│   ├── [tool_registry.py:90] 开始计时 + 执行函数
│   │   └── self._tools["run_command"](**{"cmd": "rm -rf /"})
│   │       │
│   │       └── [default_tools.py] run_command(cmd="rm -rf /")
│   │           │
│   │           ├── 危险命令黑名单检测开始...
│   │           │
│   │           ├── cmd.strip() = "rm -rf /"
│   │           ├── 遍历黑名单模式列表...
│   │           ├── 命中模式: "rm -rf /" ✅ 匹配!
│   │           │
│   │           └── return {
│   │               "success": False,
│   │               "error": "拒绝执行危险命令: rm -rf /"
│   │           }
│   │
│   ├── [tool_registry.py:94-95] 包装返回结果
│   │   ├── raw = {"success": False, "error": "..."}
│   │   └── raw["success"] is False → 走 fail 分支
│   │       └── return ToolResult.fail(raw["error"])
│   │
│   └── 返回: ToolResult(success=False, error="拒绝执行危险命令: rm -rf /")
│
├── [测试断言1] assert r.success is False
│   └── False is False? ✅ PASS ✓
│
├── [测试断言2] assert "拒绝执行" in r.error
│   └── "拒绝执行" in "拒绝执行危险命令: rm -rf /"? ✅ PASS ✓
│
└── test_dangerous_command_blocked() 结束 — PASSED ✓✓✓
```

#### (5) pytest如何生成报告

```
========================= test session starts ==========================
platform win32 -- Python 3.13.12, pytest-8.x.x
rootdir: ...\tools-os-skills-merged
collected 31 items                                                    ← 发现31个测试

tests/test_all.py::TestToolRegistry::test_default_tools_registered PASSED [  3%]
tests/test_all.py::TestToolRegistry::test_register_custom_tool PASSED  [  6%]
...                                                                    ← 执行中
tests/test_all.py::TestIntegration::test_full_data_flow PASSED       [100%]

========================= 31 passed in 0.45s =========================  ← 最终报告
```

| 信息 | 含义 |
|------|------|
| `collected 31 items` | 发现了31个测试 |
| `PASSED` | 这个测试通过 ✅ |
| `[ 3%]` | 进度百分比 |
| `31 passed` | 全部通过 |
| `in 0.45s` | 总耗时0.45秒 |
| 如果有FAILED | 会显示具体错误信息（如上文的智能提示）|

### 谁来判断对错？👉 **pytest框架 + assert语句**

- ✅ 完全自动化：无需人工介入
- ✅ 智能错误提示：告诉你哪里错了、为什么错
- ✅ 测试隔离：每个测试独立运行
- ✅ 丰富的生态系统：可以并行、覆盖率报告、CI集成
- 🎯 适用场景：正式开发、持续集成、代码质量保障

## 三种方式对比总结表

| 维度 | main.py | quick_check.py | pytest |
|------|---------|---------------|--------|
| **判断者** | 人眼 👀 | 手写check()函数 | pytest框架 🤖 |
| **自动化程度** | ❌ 手动 | ⚡ 半自动 | ✅ 全自动 |
| **失败处理** | 人眼看出错 | raise异常终止 | 记录失败，继续跑其他测试 |
| **隔离性** | ❌ 无（共享状态） | ❌ 无 | ✅ 每个测试独立环境 |
| **错误信息** | print输出 | [PASS/FAIL]文本 | 彩色终端+详细诊断 |
| **报告统计** | 无 | 通过/失败数量 | 31 passed, 0 failed, 0.45s |
| **依赖要求** | 无 | 无（纯Python） | 需安装pytest |
| **适用场景** | 演示、调试 | 无pytest环境 | 正式开发、CI/CD |

## 通俗比喻

把我们的项目比作一家**餐厅**：

| 验证方式 | 比喻 | 具体行为 |
|---------|------|---------|
| **main.py** | **试吃员** | 厨师做一道菜，试吃员品尝后说"味道还行"，但没有评分标准 |
| **quick_check.py** | **带清单的试吃员** | 试吃员拿着一张表："咸度≤3分？✅ 有葱花？✅"——按条目打钩 |
| **pytest** | **食品检测机构** | 专业机构取样→实验室化验→生成检测报告："样品A01：细菌超标❌；样品A02：合格✅"——31项全部通过 |

三者尝的是**同一道菜**（同一个 `src/` 源码），只是检查严格度和专业性不同。

## 进度检查时的讲解话术

如果被问到："你们的测试是怎么做的？"

### 推荐回答（1分钟版本）

> "我们有三层验证体系：
>
> **第一层是功能演示**（main.py），就像产品展示——让大家看到我们能做什么。
>
> **第二层是快速验证**（quick_check.py），像体检清单——逐项检查核心功能是否正常。
>
> **第三层是自动化测试**（pytest），像全面体检——125个测试用例覆盖所有模块，每次改完代码都能自动跑一遍确保没有引入bug。
>
> 特别是第三层的pytest框架，它不仅告诉我们'通过了/失败了'，还会在失败时精确指出哪一行代码出了问题、期望什么值、实际得到什么值。这大大提高了我们的调试效率。"

### 技术细节追问应对

**Q：为什么要三种方式，不直接用pytest？**

> A：不同场景需要不同工具：
> - main.py适合**演示**给别人看（有完整输出流程）
> - quick_check.py适合**快速检查**（有些同学的环境没装pytest）
> - pytest适合**正式开发**（自动化程度最高）
>
> 这体现了工程思维——根据实际情况选择合适的工具，而不是一把锤子敲所有钉子。

**Q：测试覆盖了哪些场景？**

> A：我们的125个测试分为三类：
> - **接口正确性**（24个）：验证设计是否符合MCP规范和接口定义
> - **实现完整性**（20个）：验证真实代码在各种边界情况下是否正常工作
> - **端到端集成**（31个）：验证从用户输入到最终输出的完整数据流
>
> 特别注重**安全相关测试**——比如验证危险命令是否真的被拦截、权限不足时是否真的拒绝访问。

**Q：如果测试失败了怎么办？**

> A：pytest会给出非常详细的错误信息，包括：
> 1. 哪个测试文件、哪个测试函数失败了
> 2. 具体是哪一行的assert没通过
> 3. 期望的值是什么，实际的值是什么
> 4. 相关变量的当前状态
>
> 我们通常能在几分钟内定位并修复问题。而且因为有测试保护，修复后重新跑一遍就能确认没有引入新的bug。
